Design Concept

매핑 중심에서 흐름도 중심으로

기존에는 매핑 정보를 검토하는 화면이었지만, 매핑을 시스템이 자동으로 채워주면서 검토가 불필요해졌어요.
오히려 시스템이 자동으로 채워준 정보를 잘 탐색할 수 있게 하는게 중요해졌어요.

Problem 1

복잡한 API 호출 관계를 어떻게 시각화할까?

API 간 호출 관계는 매우 복잡해요. 하나의 관계 안에도 여러 API가 얽혀 있을 수 있어서,
전부 보여주면 오히려 아무것도 파악할 수 없어요.

하나의 개인정보 DB에서 '이름'이라는 개인정보가 나갈 경우
화살표는 API 호출 방향을 의미해요. 화살표 왼쪽이 호출 주체예요.

Solution 1

지금 보고 있는 API(본API)를 기준으로
'봐야 할 관계'만 보여줬어요

1 본API가 Payload 정보를 가져오고 보내는 API
1 Payload의 출처를 알아야 매핑 정보가 맞는지 확인할 수 있어요.
2 외부로 개인정보를 보내거나 내부에서 호출 흐름이 끊기는 API
2 개인정보가 외부로 나가는지 또는 내부에서 끝나는지 파악할 때 필요해요.

API 호출 경로를 노드와 선으로 표현했어요

1 caller, callee 등의 라벨을 붙여 노드 간의 관계를 알 수 있게 했어요.
2 중요한 노드만 우선적으로 보여주되, 중략 버튼을 추가해 전체 호출 관계도 볼 수 있게 했어요.
3 제휴사/계열사 노드를 추가해 개인정보가 외부로 나가는지 내부에서 끝나는지 알 수 있게 했어요.
3 기술적 한계로 제휴사/계열사를 특정할 수 없어 외부로 나간다는 것만 알려줬어요.
4 확대/축소 버튼으로 전체 흐름을 한 화면에서 볼 수 있게 했어요.

Problem 2

API와 개인정보항목의 관계를 어떻게 보여줄까?

아래의 두가지 니즈를 동시에 충족하려면, API Payload 정보와 개인정보를 모두 보여주는 뷰가 필요했어요.

● Server Developer담당하는 API의 Payload 정보가 올바르게 매핑됐는지 확인해요.
● Privacy Manager특정 API가 어떤 동의서에 근거하여 개인정보를 보내는지 확인해요.

Solution 2

API가 주고받는 정보(Payload)와
고객이 동의한 항목을 표로 정리했어요

1 노드를 클릭하면 상세 정보를 볼 수 있는 창이 나오게 했어요.
1 표의 column이 많은 것을 고려해, 창이 오른쪽이 아닌 아래에서 나오게 했어요.
2 표는 Payload를 기준으로, Payload에 연결된 테이블, 컬럼, 서비스, 동의서, 동의항목을 볼 수 있게 했어요.
2 Privacy Manager는 동의항목이 어떤 동의서에 근거하여 수집제공되는지 확인하고,
Server Developer는 Payload가 개인정보 페이로드가 맞는지, Payload가 올바른 테이블/컬럼에 연결됐는지 확인해요.
3 가져옴/보냄 뱃지를 추가해 Payload 정보를 어디서 가져왔는지, 어디로 보냈는지 확인할 수 있게 했어요.

호출 관계에 있는 API를 연속으로 볼 때,
페이지 이동 없이 상세 정보를 확인할 수 있게 했어요

1 호출 관계에 있는 노드를 클릭하면 하단 창이 해당 노드의 정보로 바뀌어요.
2 본API와 연결된 API(caller, callee 등)에서는, 본API와 호출 관계가 있는 Payload만 보여줘 탐색 시 인지 비용을 낮췄어요.

개인정보항목 뱃지를 통해 개인정보가
어디서 출발해 어디로 나가는지 볼 수 있게 했어요

뱃지를 클릭하면 해당 항목의 흐름을 볼 수 있어요.

페이로드 흐름 보기 토글을 키면 페이로드의 호출 흐름을 볼 수 있어요.
개인정보항목은 이름이 같으면 하나로 합쳐져 보이지만, 페이로드는 고유한 값이기 때문에 개인정보 흐름을 더 명확하게 볼 수 있어요.

Problem 3

수많은 API 중 무엇이 중요한가?

개인정보를 다루는 API는 수천 개에 달하는데, 이를 모두 볼 필요는 없어요.
Privacy Manager가 우선적으로 봐야 할 API만 골라낼 수 있어야 해요.

Solution 3

개인정보의 출발점과 시작점이 되는 API만 걸러내
중요한 것에만 집중할 수 있게 했어요

1 외부로 개인정보를 직접 보내는 API만 걸러볼 수 있게 했어요.
1 개인정보가 외부로 나가는 지점이라, 과다 제공 여부를 판단할 때 가장 먼저 봐야 해요.
2 개인정보 DB를 직접 호출하는 API만 걸러볼 수 있게 했어요.
2 개인정보 흐름의 출발점이 되는 지점이라, 우선적으로 확인해야 해요.

Result

개인정보가 외부로 나가는 지점까지
명확히 볼 수 있게 됐어요

이번 개선은 전체적인 호출 흐름을 보는 기반을 마련한 작업으로, 과다 제공 판단을 위한 첫 단계였어요.

Lessons learned

정보가 복잡할수록, 하나의 기준점을 정해
시각화하는게 효과적이었어요

복잡한 API 호출 관계를 어떻게 시각화할까?
→ 본API를 기준으로 삼아, 실제로 확인이 필요한 호출 경로만 우선으로 보여줬어요
API와 개인정보항목의 관계를 어떻게 보여줄까?
→ Payload를 기준으로, API가 주고받는 정보와 개인정보 항목을 나란히 비교해서 보여줬어요
수많은 API 중 무엇이 중요한가?
→ 개인정보의 출발점과 시작점이 되는 API를 우선으로 보여줬어요
